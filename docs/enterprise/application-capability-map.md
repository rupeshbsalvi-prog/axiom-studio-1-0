# Application Capability Map

[Back to docs index](../README.md)

## Purpose

Define Axiom Studio 1.0 and Axiom Imagine X as an enterprise-grade platform organized by capabilities, not only by UI screens or employee-style roles.

## Capability Domains

| Domain | Purpose | Examples |
|---|---|---|
| Development Governance | vision, roadmap, standards, decision control | founder vision, product roadmap, ADRs, phase gates |
| Product Services | translate user/business needs into buildable requirements | research, PRDs, backlog, acceptance criteria |
| Design Services | define user experience and visual system | UX, UI, design system, prototypes |
| Architecture Services | define system shape and technical decisions | enterprise architecture, solution architecture, security architecture |
| Platform Services | shared enterprise platform capabilities | identity, RBAC, audit, notification, workflow, API gateway |
| Studio Services | creative production surfaces | Photo, Vector, Motion, Video, Typography, Brand, Whiteboard, Presentation, Asset Hub |
| Imagine X Services | intelligence and orchestration model | director planning, agents, memory, routing, critique, repair |
| Engineering Services | implementation domains | frontend, backend, database, AI, integrations, desktop |
| Operational Services | keep the platform deployable and supportable | CI/CD, monitoring, release, incident management |
| Governance Services | enterprise accountability | compliance, licensing, billing, reporting, audit |

## Platform Rule

Each capability must eventually map to a module, package, service, workflow, document owner, or runtime role.

## Locked Baseline

Changes require an ADR.
