# Web Experience Operating System Blueprint

[Back to docs index](../README.md)

## Purpose

Define Axiom Studio's public entry as a Web Experience Operating System, not a conventional website.

WEOS is the first usable expression of Axiom's product philosophy. The visitor should feel they are entering a creative operating system in the browser, not reading a product page.

## Core Principle

Do not organize the public experience as:

```text
Hero -> Features -> Studios -> Pricing -> Footer
```

Organize it as:

```text
Arrival -> Awakening -> Living Observatory -> Axiom Brain -> Creative Journey
-> Studio Exploration -> Create Live -> Community -> Developer Universe
-> Enterprise -> Future -> Workspace Portal
```

## Acts

## Act I - Arrival

The experience begins with restraint:

- Black field.
- No traditional navigation at first emphasis.
- Crystal dust.
- One beam of light.
- Particles converge.
- Crystal Core appears.
- Cursor affects nearby light and particles.

## Act II - Crystal Genesis

The Crystal Core fractures into:

- Wireframe.
- Geometry.
- Architecture.
- Living Observatory.

Everything grows rather than fades, slides, or jumps.

## Act III - Living Observatory

The user enters Axiom as a world:

- Concrete.
- Crystal.
- Titanium.
- Water.
- Fog.
- Sunlight.
- Glass bridges.
- Moving reflections.
- Environmental reactivity.

## Act IV - Axiom Brain

The intelligence system becomes visible.

Example:

```text
User writes "Create Logo"
    |
    v
Brain thinks
    |
    v
Nodes activate
    |
    v
Models route
    |
    v
Memory activates
    |
    v
Identity lock
    |
    v
Creative reasoning
    |
    v
Live generation
```

No hidden AI. Everything important is explainable.

## Act V - Studio District

Studios are represented as connected places rather than static cards:

- Photo Gallery.
- Motion Museum.
- Typography Cathedral.
- Cinema Hall.
- Brand Pavilion.
- Presentation Theater.
- Developer Hub.
- AI Observatory.

Each district should eventually contain a working mini-experience.

Community is represented as a living project ecosystem:

The developer surface should eventually include:

- Interactive API explorer.
- SDK playground.
- Shader editor.
- MCP visualization.
- Workflow graph.
- Node editor.

- Live code.

## Act IX - Enterprise

Enterprise should be experienced, not diagrammed:

- Teams.
- Projects.
- Permissions.
- Approvals.
- AI routing.
- Analytics.
- Governance.
- Audit.

## Act X - Future

The footer becomes a future roadmap environment:

- Growing crystals.
- Upcoming studios.
- Research labs.
- Experimental capabilities.
- Public roadmap.

## Component Experience States

Every major WEOS component should support:

```text
Sleeping -> Idle -> Aware -> Hover -> Focus -> Pressed -> Thinking
-> Generating -> Success -> Error -> Recover -> Sleep
```

Transitions must feel physical, not linear.

## Theme Engine

WEOS themes represent worlds, not only color modes:

- Executive.
- Museum.
- Architect.
- Designer.
- Adventure.
- Space.
- Forest.

Each theme owns lighting, particles, shaders, materials, typography, reflections, soundtrack, weather, architecture, and motion rules.

## Feasibility

Feasible with current structure if built incrementally:

- `src/platform/` remains frozen.
- WEOS lives in product/experience code.
- Three.js rendering remains behind a product-scoped Experience Director.
- Studio previews are implemented one at a time as mini-experiences.
- Performance tiers and reduced-motion modes are required before production.
